# 让 AI DM 记得住：跑团状态长期化的开发记录

dsh-qqbot 的跑团模式让一个大模型（deepseek-flash，人设「大肥鱼」）在 QQ 群里当 D&D 5e 的 DM。一场团跨好几天、几千个回合，中间对话要压缩好几次。这份文档记录从 2026-10-27 第一版到 11-07 这段时间里，DM 在哪些地方「记不住」或者「记错了」，以及每次是怎么改的。

写给以后改 `src/dnd/` 的人，也写给想在别的长期 agent 上复用这些做法的人。

## 一、问题出在哪

模型自己的「记忆」只有三样，都不可靠：

1. **对话上下文会被压缩。** 宿主的 `compactNow` 不保留尾部，除了最后一条，整段历史都换成一份几千字的摘要，工具结果原文全部丢掉。宿主的摘要模板是给写代码用的（文件、命令、待办），剧情、站位、谁欠谁钱这些很容易被挤掉，转述时还会走样。
2. **system prompt 一变，缓存就失效。** 实测存档、跨场景移动各触发过一次约 10 万 token 的重算。所以不能把每次都会变的状态往 system prompt 里塞。
3. **模型会凭印象说话。** 它即兴编出来的东西（NPC 的口供、一个不存在的营地）一旦说出口，后面就被当成事实接着用；它也会把模组剧本当成「已经发生的事」。

所以整个设计的方向是：**事实放磁盘，由工具读写；上下文里只放模型这一步需要看到的那部分，而且要放在它正好看得到的位置。**

## 二、总的原则

这是从下面那些事故里总结出来的，先列在这里：

- **团档是唯一真源。** 每群一个 `dnd/campaigns/qqbot_*_<群openid>.json`，每次工具调用都从磁盘重读，写入用临时文件加 rename。模型说的、摘要里写的，跟团档对不上时以团档为准。
- **能由代码记的，不靠模型想起来。** 去过的地点、打死的怪、任务状态、拿到的物品，工具比较每次改动的前后状态自动记账。模型只负责记工具看不到的东西（临场编的人和事、承诺、俘虏）。
- **会变的走快照，不变的锁住。** 战斗中会变的团况作为 runtime context 追加在对话末尾，前面的历史不动，缓存照样命中。背景（模组真相、本章要点、上次进度、账本）放进 system prompt，按 epoch 锁住，只在压缩或换会话时刷新。
- **规则写在模型那一步看得到的地方。** 效果从强到弱：工具返回值 > 工具说明 > 每回合注入的 DM 守则 > 仓库里的 AGENTS.md（DM 根本读不到）。
- **机密不进上下文，而不是给它打标签。** 标了「机密」的数字照样会被整行照抄。
- **剧本要写清楚 NPC 不知道什么。** 空着的地方，模型就会现编，编出来的东西就成了「事实」。
- **停团以后也要管。** 玩家收团后最爱聊团，这时候没有 DM 守则，最容易乱说。

## 三、状态存在哪、进不进上下文

| 存什么 | 位置 | 进上下文的方式 | 寿命 |
|---|---|---|---|
| 角色卡（HP、状态、资源、物品）、先攻、战场站位 | 团档 `characters` / `initiative` | 【团况 · DM 视角】快照，每变一次重发一份 | 一直在 |
| 最近记录 | 团档 `log` | 团况里的「最近」几条 | 滚动保留 30 条 |
| 剧情账本 | 团档 `chronicle` | 未了结的和最近几条进背景；其余用 `dnd_chronicle search` 查 | 只增不滚动，上限 1000 条，满了先丢最老的已了结条目 |
| 进度存档 | 团档 `summaries`，由 `dnd_progress` 按【位置】【队伍】【物品与欠账】【任务与线头】【待办】分节合并 | 只注入最后一条，作为「上次进度」 | 保留 10 条，每条最多 1500 字 |
| 剧情状态（去过的房间、见过/死了的 NPC、任务、线索、flag） | 团档 `revealed` / `npcs` / `quests` 等 | 按需出现在团况和工具结果里 | 一直在 |
| 撤销快照 | 团档旁的快照列表 | 不进上下文 | 最近 40 次改动 |
| 模组剧本 | `dnd/adventures/<id>/adventure.json` | 只注入整本真相、本章要点、当前场景的通用规则；房间 DM 笔记只给当前房间 | 剧本，不是发生过的事 |

几条细节：

- 账本分七类：事件、NPC、承诺、俘虏、线头、背景、约定。承诺、俘虏和线头天生要等一个结果，默认算「未了结」，`close` 之后才算了结。
- 同样的文字，模型重试时不会重复记账；自动记的是真的又发生了一次（又拿到一瓶药水），所以照记。
- `/dnd end` 直接停团、模型又没写过进度时，`ensureSessionSummary` 会用上一条进度加最近 15 条日志拼一条兜底，保证下次开团的「上次进度」接得上。因为只注入最后一条，拼的时候要把上一条带上，不然旧线头会丢。
- 每次掷骰有一个 `#R` 编号，撤销时不回收。`dnd_undo roll=R12` 退回那一骰和它之后的所有后果，跨回合时要确认。

## 四、上下文的三个通道

1. **system prompt**（`DndService.promptSections`）
   - `qqbot:dnd-dm`：DM 守则，固定文字。
   - `qqbot:dnd-background`：模组真相、本章要点、场景通用规则、上次进度、账本摘录，按 epoch 锁住（`PromptLatch`）。换场景、换章后，锁住的还是旧内容，新的那几行先写在团况快照里补上。
   - 停团时只注入一小段 `qqbot:dnd-paused`（见第六节）。
2. **runtime context 快照**（`DndService.stateSnapshot`）：`summarize()` 生成的团况，加上当前房间的 DM 笔记（标明「只给你裁定用，不要直接念」）。内容变了才追加一条，旧的作废。**战斗中要跨压缩保留的东西，必须进 `summarize()`。**
3. **工具返回值**：最有分量的提醒放这里，模型做那一步时正好看得到，比如再进房间时的「这里来过」、`dnd_position` 的借机和够不到提醒。

## 五、压缩

- **挑时候压。** `compact-policy.ts`：上一轮调过工具（多步结算大概率还没完）就先不压，等一个没调工具的收尾轮再压；超过阈值 1.5 倍（且不超过窗口 90%）才强制压。
- **告诉模型摘要怎么写。** DM 守则最后一条：被要求写压缩摘要时，技术小节写 (none)，篇幅留给 Critical Context，用中文逐条保留关键事件、去过的地点、NPC 身份与关系、俘虏、承诺、线头、本桌裁定；战斗中写明这一轮谁已行动、谁用过反应、挂着的效果（猎人印记、专注）。站位和 HP 不用转述，团况里有。
- **压缩后先对账。** 守则：压缩后第一次裁定之前，先对一遍最新团况的 HP、先攻指针、站位和最近记录。
- **不信摘要里的细节。** 摘要是转述，站位就走样过（见下面的事故表），所以凡是会影响裁定的东西都要有团档里的真值。

## 六、事故与修法

按时间排。每一条都来自真实跑团。

| 日期 | 现象 | 根因 | 改法 |
|---|---|---|---|
| 10-28 | 玩家说「存档」，DM 调了 `dnd_end`，之后每次掷骰都失败 | 模型以为存档要靠结束 | 每次改动本来就落盘；守则和 `dnd_end` 说明写明「存档」只需确认一句（f82e481） |
| 10-28 | DM 一上来就进第一个场景，念出 DM 笔记里的伏兵，还在反引号旁白里剧透 | 第一个房间的 DM 笔记一开团就注入了 | 加开场阶段：开场时不注入第一个场景的 DM 笔记，`dnd_story begin` 才结束开场；守则写明括号、反引号里的话群里一样看得到（cbf7742） |
| 10-29 | 模型手算箭术 +2、+1 武器，巨武器战斗用单独的 `dnd_roll` 重骰，结果没进 HP；模组改动后还手改了团档 JSON | 能力不在卡上，工具算不了；团档目录可写 | 战斗风格、专精、魔法武器写进角色卡，由 `dnd_check` 自动算；所有 QQ 会话禁止写团档目录（`noWriteRoots`）；每次加载时按模组重新对齐 `knownSites`（593ab9d） |
| 11-05 | 格罗尔走开时漏算借机攻击；狼刚咬完人，又被报成「离你十来尺」 | 同房间的站位只存在于叙事里，压缩后靠记忆 | `dnd_position` 把 5 尺格存进先攻状态，并放进团况快照；移动报用掉几尺、进了谁的触及，攻击报距离和够不够得着（87db775） |
| 11-05 | DM 守则写在 AGENTS.md 里，DM 从来没守过 | 宿主只在碰到 `dsh-qqbot/` 下的文件时才注入 AGENTS.md，而跑团会话的工作目录在上一级（2364 个回合里只注入过两回） | 守则搬进 `dnd-service.ts` 每回合注入；AGENTS.md 只给开发者看（87db775） |
| 11 月初 | 守则里写着「用 adjacent_to」，45 次移动只用了一次 | 守则越长，每条越没分量 | 守则只留每回合都要守的；某个工具怎么调写进那个工具的说明或返回值 |
| 11-05 | 再进一个去过的房间，又把「第一次进来」的描写念了一遍 | 房间描写是按首次写的 | `dnd_move` 再进房间时在返回值里提示「这里来过」 |
| 11-07 | 工具结果写着「命中【机密：AC 13】」，群里照样说「命中 AC 13」 | 数字在模型眼前就会被整行照抄，标签没用 | 怪物的 AC、HP、DC 从所有例行工具结果、日志和团况里拿掉，只给伤势词和成败；只有 `dnd_character show` 这种专门查的才给 |
| 11-07 | 把变形怪当成黑蜘蛛，说「砍的是维瑞丝，黑蜘蛛还在 19 区」 | 见下面单独一节 | 见下面单独一节 |
| 11-07 | 收团后有人问绿龙、问黑蜘蛛，模型报了没去过的地点和怪物数值，翻模组原文念后面的房间，又在团档和模组之间连着改了五次口 | 停团后不注入 DM 守则，模型什么约束都没有 | 停团时注入 `PAUSED_RULES`：先查账本，团档优先于模组；没亲历的不说、不翻模组；说错一句改正。`dnd_chronicle search` 在停团时也能用 |

### 11-07：变形怪和黑蜘蛛

这是最典型的一次，几个问题叠在一起：

1. **DM 即兴编的内容变成了事实。** 早先审问俘虏时，DM 给出的口供里有模组没写的东西。
2. **DM 确认了玩家的猜测。** 玩家说「这就是黑蜘蛛吧」，DM 答「对得上」，于是一个推测进了记忆。
3. **模组里维瑞丝的 `knows` 是空的。** 审问她时 DM 只能现编，编出了一个「断崖下营地」，后来黑蜘蛛就死在了这个营地，而模组里他应该在洞里 19 号房间。
4. **临时建的黑蜘蛛角色卡跟模组 NPC 没有关联。** 卡上记着死了，模组 NPC 的状态却还是活的；卡被移除后，死亡这件事就彻底丢了。
5. **收团后没有守则。** DM 去读模组，看到 19 号房间里还有黑蜘蛛，就反过来推断「死的是维瑞丝」。

改法：

- **存档：** 三个 NPC 在团档里记为已见过、已死亡；账本加一条未了结的「线头」，让 DM 下次开团先跟大家更正，说完再 close。
- **模组：** 给具名反派和俘虏补 `knows`，连「他不知道什么」也写（布鲁戈尔：跟黑蜘蛛没有往来）。
- **代码：**
  - `recordNpcDeath`：怪物在战斗结束时、或角色卡被移除时死亡，都写进 `npcs[id].alive=false`，卡没了死亡也还在。
  - NPC 卡片上明说：模组写了他知道什么，「这几条之外他不知道别的」；没写，「只说他亲身经历的，不要替他编新的地点、人物、据点或计划」。
  - `dnd_move` 进房间时，如果模组写在这里的 NPC 在本桌已经死了，返回值提示「本桌已死，剧本里他在场的部分作废」。
  - 给模组里的具名 NPC 临时建卡会被拒绝，改为指向 `dnd_story npc <id> fight=true`，保证卡和 NPC 是同一个人。

## 七、给 DM 的规则写在哪

| 写在哪 | 适合放什么 | 例子 |
|---|---|---|
| 工具返回值 | 只在某一步需要、而且代码能判断的提醒 | 「这里来过」、借机和够不到、本桌已死、`【待结算】`的处理说明 |
| 工具说明 | 这个工具怎么调 | `dnd_progress` 只发改动的分节 |
| DM 守则（每回合注入） | 每一回合都要守的 | 什么算行动、机密不进群、压缩后先对账 |
| PAUSED_RULES（停团时） | 平时聊到团时要守的 | 先查账本、不剧透 |
| 模组数据 | 剧情真相 | NPC 的 `knows`、DM 笔记 |
| AGENTS.md | 给开发者的约定 | DM 读不到，别把给 DM 的规则写这里 |

守则本身也要控制长度和口吻：一场跑下来，DM 会反复用同一个句式（「X 归我，但 Y 归你」「先说清」），认错时还会解释工具和日志是怎么算的。现在守则里直接点名了这些句式，一场用一次就够，认错只要一句。

## 八、新增状态时的自检

加一种会变的跑团状态之前，过一遍：

1. 它存在团档里吗？还是只存在叙事里？只在叙事里的，压缩后一定会走样。
2. 战斗中要跨压缩保留吗？要的话进 `summarize()`。
3. 它会不会改 system prompt 的文字？会的话，放进快照，别放进背景。
4. 代码能不能自动记账？能就别靠模型记。
5. 里面有没有怪物数值或 DM 机密？有就别放进例行输出。
6. 撤销时它能跟着退吗？（团档快照会带上，内存里的状态不会，比如签到表。）
7. 新增 `dnd_*` 工具时，同步更新 DM 守则、`README.md` / `README_EN.md` 的工具表和测试。

## 九、查问题的方法

- `dnd_*` 的结果永远不发到群里，群里看不到调用记录，不等于没调用。
- 会话记录在 `~/.dsh/sessions/<cwd>/<id>/session.v4.jsonl.zstd`，是一串独立的 zstd 帧。Node 的流式解压只解第一帧，要按魔数 `28 b5 2f fd` 切开逐帧解。帧内容里也可能出现魔数，解不开就和下一段合并再试。
- 战役档里，`revealed` 有的房间就是演过的，再对照 `log`、`chronicle` 和聊天记录，确认演到了哪一步。
- 一份记忆出问题时，按时间窗口把聊天、工具调用和工具结果排成一条时间线，通常能找到第一次说错的那一句。往往是一次即兴发挥，或一次对玩家猜测的确认。
